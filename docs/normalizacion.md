# Normalización a Tercera Forma Normal (3FN)

Este documento demuestra que el esquema físico de «Bodegas del Atuel» cumple
con la Primera (1FN), Segunda (2FN) y Tercera Forma Normal (3FN). La referencia
es `db/migrations/001_esquema.sql`, que define 29 tablas, 29 claves primarias y
34 claves foráneas. Las restricciones `CHECK`, `UNIQUE`, `DEFAULT` y
`NOT NULL` se agregan en `002_constraints.sql` (P1), por lo que este análisis se
centra en las dependencias funcionales y en las claves ya declaradas.

## 1. Convenciones

- Notación: `X -> Y` significa que `X` determina funcionalmente a `Y`.
- `PK` identifica la clave primaria y `FK` la clave foránea.
- Los importes usan `NUMERIC(12,2)`, los porcentajes `NUMERIC(5,2)` y las
  temperaturas `NUMERIC(4,1)`. No se usa `FLOAT`.
- `subtotal`, `descuento` (importe) y `total` son atributos derivados que se
  almacenan por rendimiento y se mantienen con triggers. No se confunden con
  `cliente.descuento`, que es un porcentaje.
- Las claves subrogadas identifican las entidades; usan
  `GENERATED BY DEFAULT AS IDENTITY`, salvo `vino.cod_vino`, que es
  `GENERATED ALWAYS AS IDENTITY` según el Anexo A.2. Las claves naturales se usan
  en `bodega` y `empleado` (CUIT) y en las tablas débiles o intermedias.

## 2. Dependencias funcionales por relación

### 2.1 Catálogos sin dependencias externas

| Relación | Dependencias funcionales |
|---|---|
| `localidad` | `id_localidad -> codigo_postal, nombre, provincia, encargado_regional` |
| `cepa` | `id_cepa -> nombre, tipo` |
| `bodega` | `cuit -> razon_social, domicilio` |
| `transportista` | `id_transportista -> razon_social, cuit, email, telefono, domicilio` |
| `maridaje` | `id_maridaje -> nombre, temperatura_servicio` |
| `finca` | `id_finca -> nombre, superficie_hectareas, departamento, provincia` |

`localidad.codigo_postal` y `transportista.cuit` son claves candidatas que
deberían declararse `UNIQUE` en `002_constraints.sql`; no cambian las
dependencias funcionales, solo agregan una clave alternativa.

### 2.2 Primer nivel con claves foráneas

| Relación | Dependencias funcionales |
|---|---|
| `sala` | `id_sala -> direccion, dia_cierre_semanal, id_localidad` |
| `empleado` | `cuit -> nombre, fecha_ingreso, salario, id_sala` |
| `parcela` | `(id_finca, nro_parcela) -> superficie_hectareas, anio_plantacion, id_cepa` |
| `vino` | `cod_vino -> nombre_comercial, tipo, anada, presentacion_ml, graduacion, precio_venta, cuit_bodega` |
| `cliente` | `id_cliente -> nombre, tipo, tipo_documento, nro_documento, direccion, id_localidad, fecha_alta, descuento` |
| `lote_uva` | `nro_lote -> id_finca, nro_parcela, campania, fecha_cosecha, kilos_cosechados, cuit_bodega` |

`parcela` es una entidad débil: su clave es `(id_finca, nro_parcela)`. El
número de parcela solo es único dentro de una finca. `lote_uva` tiene clave
simple `nro_lote`, pero su clave natural de negocio es
`(id_finca, nro_parcela, campania)`, que se declarará `UNIQUE` en `002`.

### 2.3 Relaciones `N:M` y subtipos

| Relación | Dependencias funcionales |
|---|---|
| `composicion` | `(cod_vino, id_cepa) -> porcentaje` |
| `vino_maridaje` | `(cod_vino, id_maridaje) ->` sin atributos no clave |
| `socio` | `id_cliente ->` sin atributos propios |
| `distribuidor` | `id_cliente -> zona_cobertura, nro_habilitacion` |
| `exportador` | `id_cliente -> pais_destino_principal` |
| `permiso_exportacion` | `(id_cliente, cod_permiso) -> fecha_emision, fecha_vencimiento` |
| `transportista_localidad` | `(id_transportista, id_localidad) ->` sin atributos no clave |

`composicion`, `vino_maridaje` y `transportista_localidad` implementan las
relaciones `N:M` de R9, R10 y R20. `socio`, `distribuidor` y `exportador` son
subtipos de `cliente` con `PK = FK` y `ON DELETE CASCADE`. `permiso_exportacion`
es una entidad débil de `exportador`: su clave incluye el código del permiso y
el cliente exportador.

### 2.4 Análisis, auditoría y movimientos

| Relación | Dependencias funcionales |
|---|---|
| `analisis_calidad` | `id_analisis -> nro_lote, fecha, grado_brix, ph, acidez_total` |

| `renglon_comprobante` | `(nro_comprobante, cod_vino) -> cantidad, precio_unitario, descuento, subtotal` |
| `ingreso` | `cod_ingreso -> fecha, estado, id_transportista, cuit_bodega` |
| `renglon_ingreso` | `(cod_ingreso, cod_vino) -> cantidad` |
| `transferencia` | `nro_solicitud -> id_sala, fecha_confeccion, estado` |

`stock_deposito` es una relación `1:1` con `vino` (`PK = FK`). `stock_sala` es
la tabla `N:M` de R26 y guarda la cantidad disponible por sala y vino. Los
renglones de comprobante, ingreso y transferencia son las tablas `N:M`
intermedias de R19, R23 y R25.

## 3. Primera Forma Normal (1FN)

Una relación está en 1FN si todos sus atributos son atómicos, no hay grupos
repetidos y cada fila se identifica de forma única.

Cumplimiento:

- **Atributos atómicos:** nombres, apellidos/razones sociales, documentos,
  fechas, importes, porcentajes, temperaturas y cantidades se almacenan en una
  sola columna con un único valor. No hay arreglos ni listas separadas por
  comas.
- **Sin grupos repetidos:** los ítems de un comprobante, ingreso o
  transferencia no se guardan como columnas repetidas (`vino1`, `vino2`, …).
  Se usan `renglon_comprobante`, `renglon_ingreso` y
  `renglon_transferencia`, una fila por vino del documento.
- **Relaciones `N:M` separadas:** `composicion` (vino–cepa), `vino_maridaje`
  (vino–maridaje), `transportista_localidad` (transportista–localidad) y
  `stock_sala` (sala–vino) tienen una fila por combinación.
- **Subtipos separados:** `socio`, `distribuidor` y `exportador` no agregan
  columnas opcionales a `cliente`; cada subtipo tiene su propia tabla con
  `PK = FK`.
- **Catálogos separados:** localidad, cepa, bodega, transportista, maridaje y
  finca son relaciones independientes. Las tablas que los usan guardan solo la
  clave foránea y no repiten sus descripciones.
- **Direcciones:** `direccion` se modela como un atributo textual único de uso
  comercial. Si se exigiera granularidad estricta de calle y número, habría que
  dividirla en dos columnas; el esquema actual adopta el criterio de dirección
  como unidad atómica.

Resultado: todas las relaciones tienen atributos con un único valor, clave
primaria definida y no contienen grupos repetidos.

## 4. Segunda Forma Normal (2FN)

Una relación está en 2FN si está en 1FN y todo atributo no primo depende de la
clave primaria completa, no de una parte de ella.

Las tablas con clave simple (`localidad`, `cepa`, `bodega`, `transportista`,
`maridaje`, `finca`, `sala`, `empleado`, `vino`, `cliente`, `lote_uva`,
`analisis_calidad`, `auditoria_precio`, `comprobante`, `ingreso`,
`transferencia`, `stock_deposito`) no pueden tener dependencias parciales,
porque su clave primaria es un solo atributo.

Las tablas con clave compuesta cumplen 2FN:

- **`parcela`**: `(id_finca, nro_parcela)` determina `superficie_hectareas`,
  `anio_plantacion` e `id_cepa`. Ninguno depende solo de `id_finca` ni solo de
  `nro_parcela`.
- **`composicion`**: `(cod_vino, id_cepa)` determina `porcentaje`. El
  porcentaje no depende solo del vino ni solo de la cepa.
- **`vino_maridaje`** y **`transportista_localidad`**: no tienen atributos no
  clave; toda la fila depende de la clave completa.
- **`permiso_exportacion`**: `(id_cliente, cod_permiso)` determina las fechas
  de emisión y vencimiento.
- **`renglon_comprobante`**: `(nro_comprobante, cod_vino)` determina
  `cantidad`, `precio_unitario`, `descuento` y `subtotal`.
- **`renglon_ingreso`**: `(cod_ingreso, cod_vino)` determina `cantidad`.
- **`renglon_transferencia`**: `(nro_solicitud, cod_vino)` determina
  `cantidad`.
- **`stock_sala`**: `(id_sala, cod_vino)` determina `cantidad`.
- **`socio`**, **`distribuidor`** y **`exportador`**: la clave es
  `id_cliente`; en `distribuidor` y `exportador` los atributos propios dependen
  de ese único cliente.

En consecuencia, todas las relaciones están en 2FN.

## 5. Tercera Forma Normal (3FN)

Una relación está en 3FN si está en 2FN y ningún atributo no primo depende
transitivamente de la clave primaria.

### 5.1 Dependencias transitivas eliminadas

- **Localidad, provincia y encargado regional:** `sala` y `cliente` guardan
  solo `id_localidad`. La provincia y el encargado regional viven en
  `localidad`. Si se copiaran en `sala` o `cliente`, existiría
  `id_sala -> id_localidad -> provincia/encargado_regional`, una dependencia
  transitiva. No ocurre en el esquema.
- **Sala en empleado:** `empleado` guarda `id_sala`, no el nombre ni la
  dirección de la sala. Los datos de la sala dependen de `sala`, no del
  empleado.
- **Cepa en parcela:** `parcela` guarda `id_cepa`; el nombre y el tipo de la
  cepa dependen de `cepa`, no de la parcela.
- **Bodega en vino, lote e ingreso:** las tres tablas guardan la clave
  `cuit_bodega`; la razón social y el domicilio dependen de `bodega`. No se
  repiten en las tablas hijas.
- **Localidad en cliente y sala:** ambos guardan `id_localidad`; los datos
  geográficos y el encargado regional no se duplican.
- **Subtipos de cliente:** `zona_cobertura` y `nro_habilitacion` dependen del
  distribuidor; `pais_destino_principal` depende del exportador. Se separaron
  en `distribuidor` y `exportador` para evitar columnas nulas y dependencias
  que solo aplican a un subtipo.
- **Permisos de exportación:** las fechas dependen de la combinación
  `(id_cliente, cod_permiso)`, no de `cliente` ni de `exportador` por
  separado.
- **Precio aplicado en el renglón:** `precio_unitario`, `descuento` y
  `subtotal` son el valor histórico de la operación, no una copia del precio
  actual del vino. Dependen de la fila del renglón y preservan la venta aunque
  cambie `vino.precio_venta`.
- **Totales del comprobante:** `subtotal`, `descuento` y `total` son derivados
  de los renglones. Se almacenan por rendimiento y se recalculan con triggers;
  no determinan atributos de otras tablas.
- **Departamento y provincia en finca:** se mantienen como atributos
  descriptivos. El nombre de un departamento puede repetirse en provincias
  distintas (por ejemplo, «San Martín»), por lo que `departamento` por sí solo
  no determina `provincia`. No hay una dependencia transitiva directa que
  obligue a crear tablas de departamento o provincia.
- **Tipo de cliente:** `cliente.tipo` es un discriminador de la jerarquía. No
  determina por sí solo `descuento`; el descuento es un dato propio de cada
  cliente y puede variar entre clientes del mismo tipo.

### 5.2 Atributos derivados y de auditoría

- `renglon_comprobante.subtotal` se calcula a partir de `cantidad`,
  `precio_unitario` y `descuento`.
- `comprobante.subtotal`, `comprobante.descuento` y `comprobante.total` se
  recalculan a partir de los renglones.
- `auditoria_precio` es una tabla histórica: guarda `precio_anterior`,
  `precio_nuevo`, `fecha_hora` y `usuario`. No modifica la normalización del
  vino; registra el cambio de precio.
- `empleado.salario` y `vino.precio_venta` son datos vigentes; la antigüedad
  laboral no se almacena porque se calcula con `fn_antiguedad_anios`.

### 5.3 Verificación

Para cada una de las 29 tablas se cumple:

1. Está en 1FN: atributos atómicos y sin grupos repetidos.
2. Está en 2FN: ningún atributo no primo depende de una parte de la clave.
3. No hay dependencias transitivas: los atributos no clave dependen
   directamente de la clave primaria de su relación.

No se detectó un desvío de 3FN que justifique un issue `cambio-schema`. Las
claves candidatas pendientes (`localidad.codigo_postal`,
`transportista.cuit`, `vino(nombre_comercial, anada, presentacion_ml)` y
`lote_uva(id_finca, nro_parcela, campania)`) son restricciones de unicidad de
`002_constraints.sql`, no dependencias transitivas.

## 6. Relaciones `N:M` y `1:N` implementadas

| Relación | Cardinalidad | Implementación |
|---|---|---|
| `vino` — `cepa` | `N:M` con `porcentaje` | `composicion(cod_vino, id_cepa, porcentaje)` |
| `vino` — `maridaje` | `N:M` | `vino_maridaje(cod_vino, id_maridaje)` |
| `cliente` — `socio` | `1:0..1` | `socio(id_cliente)` con `PK = FK` |
| `cliente` — `distribuidor` | `1:0..1` | `distribuidor(id_cliente, ...)` con `PK = FK` |
| `cliente` — `exportador` | `1:0..1` | `exportador(id_cliente, ...)` con `PK = FK` |
| `exportador` — `permiso_exportacion` | `1:N` | `permiso_exportacion(id_cliente, cod_permiso, ...)` |
| `transportista` — `localidad` | `N:M` | `transportista_localidad(id_transportista, id_localidad)` |
| `comprobante` — `vino` | `N:M` con atributos | `renglon_comprobante(nro_comprobante, cod_vino, ...)` |
| `ingreso` — `vino` | `N:M` con atributos | `renglon_ingreso(cod_ingreso, cod_vino, cantidad)` |
| `transferencia` — `vino` | `N:M` con atributos | `renglon_transferencia(nro_solicitud, cod_vino, cantidad)` |
| `sala` — `vino` | `N:M` con atributos | `stock_sala(id_sala, cod_vino, cantidad)` |
| `vino` — `stock_deposito` | `1:1` | `stock_deposito(cod_vino, cantidad)` con `PK = FK` |

## 7. Conclusión

El esquema físico de `001_esquema.sql` está en 3FN. Las dependencias
funcionales se concentran en la clave primaria de cada relación, las claves
compuestas no arrastran dependencias parciales y las dependencias transitivas
se resolvieron mediante catálogos, subtipos, tablas `N:M` y renglones. Los
atributos derivados y de auditoría se mantienen de forma controlada por
triggers y funciones, sin romper la normalización lógica del modelo.

Las restricciones de integridad que faltan (`CHECK`, `UNIQUE`, `DEFAULT` y
`NOT NULL`) corresponden a `002_constraints.sql`; cuando P1 las agregue, este
documento y el diccionario de datos deberán regenerarse para reflejar el
esquema completo.
